# 航运账单 Agent：问题与解决方案说明

本文根据 V2 的实际修改、回归测试和错误账单排查整理。已实现的保护机制与尚待完善的提取问题分别说明，避免把“转人工复核”误当作“金额校验准确”。

## 一、项目要解决的问题

航运账单来自邮件、PDF、图片和表格，字段名称、单据结构和费用描述各不相同。系统既需要提取金额，也需要确认金额属于哪条费用、哪张单据、哪个记账主体，以及是否有依据修改旧账。

调整后的处理顺序是：

```text
解析文件并保留来源证据
→ 提取逐条费用和单据字段
→ 按主体及业务身份检索旧账候选
→ 提出变更方案
→ 程序校验
→ 预览与人工复核
→ 事务提交账本、审计及来源状态
```

## 二、已实施的调整

| 问题 | 原因 | 解决方式 | 当前状态 |
|---|---|---|---|
| 不同材料的金额字段难以统一 | Amount、Rate、Total、Balance Due 等含义不同 | 建立统一模型，分别保存明细金额、单价、原币、结算金额、汇率、原单总额、已付额和余额 | 数据结构与校验已实现；真实模型填值准确性仍需验收 |
| 同名费用无法准确定位 | 仅靠费用名或新金额匹配，可能混淆两条 handling | 每条费用使用稳定 ID；单据、类型化编号和费用行分开保存；多候选进入复核 | 已实现并有回归测试 |
| 不同公司的同号账单可能互相覆盖 | 检索未限定记账主体 | 查询、文件处理状态和提交均限定主体；提交阶段锁定账套 | 已实现并有主体隔离测试 |
| 金额不同就自动更新 | 将差异直接当成修改依据 | 要求费用身份唯一、修订范围获准、字段证据充分；无法确认时保留旧账并复核 | 已实现；明确修订的真实模型识别仍需验证 |
| 更新丢失旧字段或历史 | 用新材料重新构建整条旧记录 | 使用字段补丁，缺失字段继承旧值；保留版本与历史，记录前后值和依据 | 已实现并有字段继承、版本和审计测试 |
| 重复上传或多个预览重复新增 | 仅靠文件名或不完整查重规则 | 结合主体、文件摘要、处理配置和记录版本复用；提交时重新检查新增候选 | 已实现并有重复提交测试 |
| 账已更新、审计却写入失败 | 逐笔写入并分别提交 | 账本、审计、来源状态在同一事务提交；失败回滚，旧版本不能覆盖新版本 | 已实现；SQLite 已离线验证，真实 MySQL 未联调 |
| 图片和邮件附件内容没有进入处理流程 | 图片只返回占位文字，附件只记录名称 | 接入本地文件 OCR/OSS 流程，递归解析附件，保留来源块、原始文件及不可变解析观察记录 | 流程已实现，OCR/OSS 使用替身测试；真实服务未验收 |
| 模型摘要为对象时触发字符串校验错误 | 返回类型与预期不一致 | 响应入口将非文本摘要转换为 JSON 文本，原始结构保留在元数据；提示词明确要求字符串或 null | 已修复并增加回归测试 |
| 演示与真实数据库走不同判断规则 | 数据库分支绕过部分验证与冲突处理 | 统一规划、校验和提交链路；演示仅替换模型结果和数据库，不替换业务规则 | 已实现；UI 默认预览，明确提交后才写业务账本 |
| 临时文件、缓存和启动行为可能写入 C 盘 | 依赖系统默认目录 | 显式配置 D 盘运行目录，并重定向 Streamlit 全局文件和磁盘缓存路径 | 已实现并做路径检查；原 C 盘文件未清理或修改 |

## 三、错误账单样例揭示的待完善问题

该样例中明细为 300.0000 USD，单据总额为 245.0000 USD，差额为 55.0000 USD。系统应该明确报告“金额合计不一致，整单待复核，未入账”。

目前截图中的 PENDING_REVIEW 说明处理被保守拦截，但不能单独证明程序实际比较了 300 与 245。

### 1. 原文已读取，结构化字段仍缺失

**现象：** 解析记录包含 300.0000、245.0000 和 USD，截图却显示币种未知、总额未提取。

**定位：** 本次 ocr_processed=False，使用 PDF 原生文字读取。文字已经进入程序构造的模型输入；问题位于文字到结构化字段的转换阶段。当前记录不足以进一步区分模型理解遗漏与返回字段不匹配。

**解决方式：**

- 保留 PDF 表格的行列或坐标信息，减少费用名、币种、金额和日期粘连。
- 向模型提供完整字段结构、字段类型及合法枚举，并校验返回值。
- 将模型请求材料、原始 JSON 响应和规范化结果分别记录在 D 盘，排除凭据，便于定位数据在哪一步丢失。
- 将结构化字段绑定到具体原文块；不能仅因证据数组出现 USD，就假定币种字段一定正确。

### 2. 模型遗漏总额，导致合计检查无法执行

**现象：** 当前程序在没有任何 document_total 时跳过合计比较。

**解决方式：** 区分“原文没有总额”与“原文有总额但模型漏提取”。从表格位置或带标签文本建立总额候选；有候选却没有结构化总额时，明确提示无法完成核对并转复核。原文确实没有总额时保留这一事实，不能自行生成总额冒充原文。

**验收条件：** 能明确输出明细合计 300.0000 USD、单据总额 245.0000 USD、差额 55.0000 USD；提交后仍保持待复核，不写入本单费用。

### 3. 排除项类别与程序枚举不一致

**现象：** 模型返回 item_type="总计费用"，程序原本仅接受 conditional_charge、summary_line、historical_reference、other。

**当前情况：** 工作区已增加未知类别转为 other 的兜底，能减少直接枚举报错，但没有保证原类别语义被正确保留。

**解决方式：** 提示词列出合法值，对已确认的别名建立精确映射，例如“总计费用”对应 summary_line，并保留原始类别。真正未知的类别应明确记录问题，不能单靠统一转成 other 就认定提取正确。

### 4. 界面只显示“处理错误：失败”

**原因：** 一部分模型问题使用 description 字段，界面主要读取 error 或 message，因而丢失了可读说明。

**解决方式：** 在响应入口统一问题结构，例如 code、category、message、source_id、field、severity。界面区分金额校验、字段缺失、模型格式和系统异常，显示具体原因；技术详情放到展开区域。

### 5. 缺失币种被默认填成 USD

**本次复核发现：** 当前 agent.py 在 currency 缺失时填入 USD，导致“未知币种保持 null”的回归测试失败。

**解决方式：** 删除无依据的默认币种。原文明示 USD 或有适用且经确认的币种规则时才规范化；无法确定时保留 null 并人工核对。金额已识别不代表币种也已确定。

**验收条件：** 含 USD 的材料正确提取 USD；仅有不明确的货币符号或缺少币种时仍为 null；不以默认值掩盖模型漏提取。

## 五、可用于项目介绍的简述

本次调整主要解决账单字段不统一、同名费用难以匹配、跨主体串账、无依据更新和审计不完整等问题。实现上，将流程拆分为费用提取、候选检索、变更规划、程序校验、人工复核和事务提交；通过稳定费用 ID、字段证据、补丁更新、版本检查和幂等控制保护账本。

当前已建立保守拦截机制，但真实材料的结构化提取仍有待完善。下一步重点是改善 PDF 表格文本、约束模型返回结构、补齐总额漏提取检测，并让界面明确展示金额差额和复核原因。

实现与验证可参考本项目的 README.md、docs/verification-2026-11-02.md，以及 agent.py、validator.py、smart_crud.py、database.py 和 workflow_db.py。本说明所有新增文件与测试输出均位于 D 盘；可控 C 盘文件写入为 0 B。
