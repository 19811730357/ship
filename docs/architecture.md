# 架构说明

## 系统概述

航运智能账单助手 V2 是一个基于大模型决策的智能账单处理系统。核心创新在于**让大模型主导操作决策，程序负责验证保障**。

## 核心流程

### 1. 输入处理

```
材料文件 → 解析器 → 统一的材料结构
旧账JSON → 加载器 → Ledger对象
```

### 2. Agent决策

```
材料内容 + 旧账 → LangChain Agent → AgentDecisionBatch
                        ↓
                 包含每个费用的：
                 • suggested_operation (CREATE/UPDATE/NO_CHANGE)
                 • operation_reasoning
                 • matched_record_id
                 • confidence (HIGH/MEDIUM/LOW)
                 • 业务数据 + 证据
```

### 3. 程序验证

```
AgentDecision + Ledger → Validator → ValidationResult
                              ↓
                       独立执行：
                       • 基础字段验证
                       • 金额币种验证
                       • AR/AP一致性验证
                       • 独立匹配旧账
                       • 操作合理性检查
```

### 4. 冲突解决

```
AgentDecision + ValidationResult → resolve_operation() → FinalOperation
                                            ↓
                                    策略决策：
                                    • 一致 → 采纳
                                    • 验证失败 → PENDING_REVIEW
                                    • 模型高置信 + 程序歧义 → 信任模型
                                    • 其他冲突 → PENDING_REVIEW
```

### 5. 应用操作

```
FinalOperation + Ledger → apply_operation() → 更新后的Ledger
                                ↓
                         根据操作类型：
                         • CREATE → 添加新记录
                         • UPDATE → 合并字段变更
                         • NO_CHANGE → 只记录操作ID
                         • PENDING_REVIEW → 不应用
```

## 数据模型层次

### 决策链路

```
AgentDecision (模型的建议)
    ↓
ValidationResult (程序的验证)
    ↓
FinalOperation (最终操作)
    ↓
LedgerRecord (账本记录)
```

### 关键模型

**AgentDecision**
- 模型给出的操作建议
- 包含完整的业务数据和证据
- 带有置信度评估

**ValidationResult**
- 程序的独立验证结果
- 列出发现的问题
- 给出程序的操作建议

**FinalOperation**
- 合并模型和程序的决策
- 记录冲突解决过程
- 包含完整审计追踪

**LedgerRecord**
- 最终持久化的账本记录
- 保留历史审计链
- 支持扩展字段

## 关键设计决策

### 1. 为什么让模型决策操作类型？

**传统方案的问题**：
- 程序规则无法处理复杂的自然语言表达
- 硬编码匹配规则覆盖不全
- 无法理解"修改"、"调整"等语义

**模型决策的优势**：
- 理解复杂引用（"上月的操作费"）
- 识别修改意图（"调整为"、"改为"）
- 处理条件逻辑（"如果...则..."）

### 2. 为什么保留程序验证？

**不能完全依赖模型**：
- 模型可能判断错误
- 关键业务规则需要确定性保障
- 金额计算、币种验证等需要精确检查

**程序验证作为安全网**：
- 独立重新匹配旧账
- 验证金额、币种、AR/AP一致性
- 发现冲突时提示人工复核

### 3. 冲突解决策略

**双重判断的价值**：
- 模型和程序一致 → 增强信心
- 模型更乐观 + 高置信度 → 可以信任
- 存在冲突 → 转人工复核，安全优先

## 与旧版本对比

| 方面 | V1（旧版） | V2（新版） |
|------|-----------|-----------|
| **Agent职责** | 仅信息提取 | 语义理解 + 操作建议 |
| **操作决策** | 程序规则决定 | 模型建议 + 程序验证 |
| **冲突处理** | 无（程序是唯一决策者） | 双重判断 + 智能合并 |
| **数据模型** | 扁平结构 | 分层：Decision→Validation→Final |
| **审计追踪** | 简单记录 | 完整决策过程 + 冲突解决 |
| **模型能力利用** | 低（仅提取） | 高（决策 + 推理） |
| **可解释性** | 程序逻辑可追踪 | 模型reasoning + 程序validation |

## 技术栈

- **LLM框架**: LangChain
- **模型**: 阿里云通义千问（OpenAI兼容接口）
- **数据验证**: Pydantic V2
- **精确计算**: Python Decimal
- **Web界面**: Streamlit
- **测试**: Pytest
- **文件解析**: python-docx, openpyxl, PyPDF2

可以引入RAG：

- 合同条款查询

## 安全性考虑

1. **数据隔离**：按记账主体严格隔离
2. **操作幂等性**：operation_id防止重复应用
3. **审计完整性**：每个操作都有完整追踪
4. **密钥安全**：通过环境变量配置，不入代码
5. **验证兜底**：程序验证防止模型错误

## 性能考虑

1. **模型调用优化**：批量处理决策
2. **缓存策略**：旧账匹配结果可缓存
3. **并发处理**：多文件可并行解析
4. **增量更新**：只更新变更字段
