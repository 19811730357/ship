# 面试回答：如何防止重复入账和并发冲突

## 问题：如何防止重复上传、重复点击以及过期预览导致的重复入账？

---

## 核心回答框架

### 一、重复问题的分类

我们系统中有两类重复需要分别处理：

1. **文件重复**：同一份文件被多次上传
2. **业务重复**：不同文件实际对应同一笔费用
3. **并发重复**：同一预览被多次提交，或多个预览同时提交
4. **过期重复**：基于旧数据的预览覆盖了新数据

---

### 二、技术方案总览

我们采用**分层防御**策略：

```
第一层：文件去重（SHA-256）
第二层：预览状态拦截（内存）
第三层：数据库事务锁（主体锁 + 行锁）
第四层：乐观锁版本控制（version 字段）
```

---

### 三、详细实现（重点讲第三、四层）

#### 1. 文件去重（简要带过）

```python
# 使用 SHA-256 计算文件内容摘要，不依赖文件名
file_hash = hashlib.sha256(file_content).hexdigest()

# 主键设计：(记账主体 + 文件摘要 + 配置版本)
# 同一文件改名后仍能识别；不同主体可分别处理
```

#### 2. 预览状态拦截（简要带过）

工作流在内存中保存已提交的 `item_id`，防止同一预览重复提交。但这只能防止单个工作流实例内的重复，进程重启后失效。

#### 3. 数据库并发控制（重点）

**主体级别事务锁**：

```python
def _lock_scope(self, accounting_entity):
    """获取记账主体的事务锁，串行化同主体的所有提交"""
    # MySQL: INSERT IGNORE + SELECT ... FOR UPDATE
    # 锁定整个记账主体，防止并发修改
    self._execute("SELECT accounting_entity FROM billing_scope_locks 
                   WHERE accounting_entity=? FOR UPDATE", 
                   (accounting_entity,))
```

**作用**：两个用户同时提交同一主体的操作时，后者必须等待前者完成。

**业务候选检查**：

```python
def _check_create_candidates(self, plans, accounting_entity, baseline_records):
    """在事务锁内，重新查询业务候选，检测是否已被其他事务创建"""
    for plan in plans:
        if plan["operation"] == "CREATE":

```

**处理场景**：
- 两个不同的扫描件，实际对应同一笔费用
- 两个预览都判断"需要新增"
- 提交时，先提交的创建成功，后提交的会被拦截

#### 4. 乐观锁版本控制（核心重点）

**什么是乐观锁？**

乐观锁假设冲突很少发生，不在读取时加锁，而是在提交时检测是否有并发修改。我们使用递增的整数版本号（从1开始）作为冲突检测标记。

**版本号的生命周期**：

```
1. 新建记录：version = 1
2. 第一次修改：version = 2
3. 第二次修改：version = 3
...依次递增
```

**两层版本检查机制**：

```python
# 第一层：代码层检查（提交事务开始后）
def commit_plans(self, plans, ...):
    with self.transaction():
        self._lock_scope(accounting_entity)  # 获取主体锁
        
        for plan in plans:
            if plan["operation"] == "UPDATE":
                # 读取数据库当前版本
                current = self.get_record(record_id, for_update=True)
                
                # 比较：数据库当前版本 vs 预览时记录的版本
                if current.version != plan["expected_version"]:
                    raise ValueError("记录版本已变化，请重新预览")
```

**FOR UPDATE 的作用**：在 MySQL 中锁定该行，防止其他事务修改。

```python
# 第二层：SQL 层检查（实际写入时）
def save_ledger_record(self, record, expected_version=None):
    # 1. 验证新版本号是旧版本+1
    if record.version != expected_version + 1:
        raise ValueError("更新后的记录版本必须递增一次")
    
    # 2. 执行带版本条件的 UPDATE
    cursor = self._execute("""
        UPDATE billing_charge_lines 
        SET amount=?, version=?, ...
        WHERE record_id=? 
          AND accounting_entity=?
          AND version=?  -- 关键：只有版本匹配才更新
    """, (..., record.version, record_id, entity, expected_version))
    
    # 3. 检查影响行数
    if cursor.rowcount != 1:
        raise ValueError("记录版本已变化，请重新预览")
```

**SQL 层的原子性保证**：

```sql
UPDATE billing_charge_lines 
SET version = 6, amount = 150
WHERE record_id = 'abc-123' 
  AND version = 5;  -- 只有当前版本是5时才更新

-- 如果数据库中version已经是6（被其他事务改过）
-- WHERE条件不匹配，rowcount = 0，更新失败
```

### 四、完整的并发场景演示

**场景**：两个用户同时修改同一条记录

```
初始状态：record_id="abc-123", version=5, amount=100

时刻1：用户A生成预览
  - 读取数据库：version=5
  - 预览记录：expected_version=5, 新amount=150, 新version=6

时刻2：用户B生成预览（同时进行）
  - 读取数据库：version=5（用户A还没提交）
  - 预览记录：expected_version=5, 新amount=200, 新version=6

时刻3：用户A提交（先到达）
  - 获取主体锁 ✓
  - 第一层检查：数据库version=5 == expected_version=5 ✓
  - 第二层检查：执行 UPDATE ... WHERE version=5，成功 ✓
  - 提交事务，释放锁
  - 数据库状态：version=6, amount=150

时刻4：用户B提交（随后到达）
  - 获取主体锁（等待用户A释放） ✓
  - 第一层检查：数据库version=6 != expected_version=5 ✗
  - 抛出异常："记录版本已变化，请重新预览"
  - 事务回滚
```

---

### 五、为什么需要两层检查？

**面试官可能追问**：第一层检查已经比对了版本，为什么还需要第二层？

**回答**：

1. **第一层（代码层）**：尽早发现冲突，避免执行后续无效操作，提升性能
2. **第二层（SQL层）**：防御性编程，即使第一层有bug或被绕过，数据库层面仍能保证原子性

这是**纵深防御**思想：关键的数据一致性逻辑不能只依赖一层保护。

---

### 六、乐观锁的权衡

**面试官可能追问**：为什么不阻止所有并发修改字段，只阻止真正冲突的字段？

**回答**：

这是**设计权衡**。字段级冲突检测在财务系统中不适用：

**问题示例**：
```
用户A预览时看到：version=5, amount=100, currency="USD"
期间用户B修改了：currency="CNY"（发现之前录错了）
如果允许用户A基于旧状态提交amount=150：
结果：amount=150（按USD理解）+ currency="CNY"（已改成人民币）
风险：币种和金额不匹配，数据逻辑错误
```

**原因分析**：

1. **字段强关联**：币种、金额、发票方、单据号等字段有业务依赖关系
2. **校验规则依赖完整状态**：我们的 `validate_extracted_charge` 需要看到完整记录
3. **审计完整性**：每次修改必须基于准确的前置状态，确保审计链条完整
4. **实现复杂度**：版本号方案简单可靠，字段级冲突检测容易遗漏隐含依赖

**实际影响**：

- 在快速操作场景下，版本冲突很少发生
- 如果发生冲突，用户重新预览即可，代价可接受
- 这是在**正确性**和**用户体验**之间选择了正确性

---

### 七、总结（30秒电梯演讲版）

我们的并发控制采用**四层防御**：

1. **文件SHA-256去重**：防止同一文件重复处理
2. **预览状态拦截**：防止单次会话内的重复提交
3. **数据库主体锁 + 业务候选检查**：防止不同文件对应同一笔费用的并发新增
4. **乐观锁版本号**：两层检查（代码层 + SQL层）防止过期预览覆盖新数据

核心是**乐观锁**：用递增版本号检测并发修改，SQL层面用 `WHERE version=?` 保证原子性，任何基于旧版本的修改都会被拒绝并要求重新预览，确保数据一致性和审计完整性。
