## 当前图片／EML 失败的实际原因

只读检查实际 `.env`：设置了题方 `OCR_URL`，但没有设置 `OCR_BACKEND` 和 `VISION_MODEL`。工作流缺省采用 `vision`，因此不会因为填写了 `OCR_URL` 就自动调用题方接口。

最新图片解析观察记录 `image_ocr_failed`，原因是“视觉识别未配置，请设置 VISION_MODEL、服务地址和 API 密钥”。

实际 EML 的一份解析观察中，正文和两个 MBL/HBL 文字型 PDF 附件成功，内嵌 JPG 失败，错误是旧 remote 路线下“本地OCR需要配置OSS”。因此应描述为邮件部分内容读取成功，完整图片与费用处理阻塞。

现有题方客户端只实现 `POST JSON`，其中 `file` 为远端能够读取的 URL。选择 `OCR_BACKEND=remote` 可对齐接口，但本地上传还需要可达文件 URL；当前本地桥接只有 OSS。是否支持 multipart、Base64 或配套上传接口，现有请求示例没有说明，不能擅自假定。

## 整改顺序及完成判据

1. **题方 OCR 闭环。** 确定真实输入协议和文件上传／可达链接方式；对齐活动后端。实际图片、扫描 PDF、EML 图片附件均取得真实响应，并核对响应结构。配置不足要明确指出缺项。
2. **表格与主体角色。** 建立至少一份多 sheet Excel、一份含费用表格的 Word 及不同主体角色样本；将实际单元格结构传给提取阶段，标注签发方、付款方及应收／应付。
3. **真实模型标注评测。** 对现有 PDF1、PDF2、图片、EML 和错误修改件制作人工标准答案，比较单号、逐条费用、金额、币种、方向和新增／更新结果。统计漏提、多提、不必要复核、错误自动放行，不使用测试预填值冒充真实模型输出。
4. **运行追踪和闭环。** 同一运行 ID 记录识别、提取、补提取、候选提议、校验及提交；保存原始与规范化结果、模型／提示词版本、耗时，排除密钥和 Base64 请求体。支持不重新调用服务的离线重放。
5. **测试账套端到端。** 上传实际文件→识别→提取→预览→提交→SQL／审计核对；重复上传不重复入账；300／245显示差额55且本单费用不入账；正常账单应自动生成可提交预览。
